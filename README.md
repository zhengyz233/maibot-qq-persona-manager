# QQ 人格管理插件（qq-persona-manager）

给 MaiBot（麦麦）用的插件，在 QQ 里用两条指令管理麦麦的人格：

| 指令 | 作用 |
|---|---|
| `/人格查询` | 把麦麦当前人格拆成 `#人设` / `#行为风格` / `#表达风格` 三段，以 **QQ 合并转发（聊天记录卡片）** 的形式发到当前的聊天流，每段正文最前面自带分类标签。**默认只在私聊生效**，群聊需打开开关 |
| `/人格修改 需求` | 用麦麦自己的 `replyer` / `planner` 模型判断这条需求属于哪一类，与原文融合后**直接热更新**，改完立即生效，不用重启 |
| `/人格优化` | 让模型**重新分类 + 压缩精简**当前三段人格，保持语义不变地把人格改短，**降低每次请求的人格 token 开销**；成功后再附一张人格卡片回显优化结果。**默认只在私聊生效**，群聊需打开开关 |
| `/人格帮助` | 显示指令说明（附带的，方便你随时查） |

**白名单机制**：只有白名单里的 QQ 号能触发上面这些指令。非白名单用户发指令时，麦麦会在聊天流里回复 **"您无权进行此类操作"**。

---

## 一、先确认环境

| 项目 | 要求 |
|---|---|
| MaiBot 版本 | **v1.3.0 及以上**（新版插件 SDK 体系；`Config` 目录里应该能看到 `config/bot_config.toml`） |
| 插件 SDK | `maibot-plugin-sdk` 2.x。MaiBot 自带依赖里通常已经有了 |
| 模型 | `model_config.toml` 里 `[model_task_config.replyer]` 或 `[model_task_config.planner]` **至少有一个配了能用的模型**（插件默认先试 replyer，不行自动改用 planner） |
| QQ 适配器 | 需要支持合并转发的实现（NapCat / Lagrange 等 OneBot 实现都支持）。万一失败，插件会自动退回普通文本发送 |

> 怎么确认 SDK 在不在？如果插件加载时报 `ModuleNotFoundError: No module named 'maibot_sdk'`，在 **MaiBot 的目录**里执行一次：
> - 用 uv 装的：`uv add maibot-plugin-sdk`
> - 普通 pip 装的：`pip install maibot-plugin-sdk`

## 二、安装（4 步）

### 第 1 步：把插件文件夹放进去

**方式一：直接复制**

把整个 `qq-persona-manager` 文件夹复制到 MaiBot 的 `plugins` 目录下。

**方式二：用 git 克隆（方便以后更新）**

在 MaiBot 根目录执行：

```bash
git clone https://github.com/<你的用户名>/<仓库名>.git plugins/qq-persona-manager
```

以后更新只要：

```bash
cd plugins/qq-persona-manager && git pull
```

无论用哪种方式，最终结构必须是：

```
MaiBot/
├── config/
├── data/
└── plugins/
    └── qq-persona-manager/      ← 就是这个文件夹
        ├── _manifest.json
        ├── plugin.py
        ├── README.md
        └── LICENSE
```

⚠️ 是复制**文件夹本身**，不要把里面的两个文件散着丢进 `plugins/`。

### 第 2 步：填白名单（重要，不填谁都用不了）

启动 MaiBot，然后二选一：

**方式 A（推荐，点点鼠标就行）**
1. 浏览器打开 MaiBot 的 WebUI：`http://127.0.0.1:8001`
2. 左侧进入 **插件** 页 → 找到 **QQ 人格管理（查询 / 修改）**
3. 打开 **白名单** 卡片，在 `whitelist` 里把你的 QQ 号加进去，保存

**方式 B（直接改文件）**

插件第一次加载后会自动生成 `plugins/qq-persona-manager/config.toml`。仓库里的
`config.toml.example` 就是它的完整内容 —— 如果你的 `config.toml` 缺失或损坏，
把它复制过去、改名为 `config.toml` 即可。

用记事本打开，改成（**请整体保留 `[plugin]` 段**）：

```toml
[plugin]
config_version = "1.0.0"        # 必须存在且不能为空，否则插件会加载失败

[access]
whitelist = ["123456789", "987654321"]
deny_message = "您无权进行此类操作"
notify_on_deny = true
```

- ⚠️ `[plugin]` 段是 MaiBot 的**硬性要求**，`config_version` 留空或删掉会导致
  插件页报「缺少 `[plugin]` 配置节」并暂停插件功能，详见下方「出问题了？」。
- `whitelist`：能使用指令的 QQ 号，**写纯数字或用 `qq:123456789` 都行**，多个用英文逗号隔开
- **白名单为空时，所有人都会被拒绝**（这是故意的安全设计）

填完保存，插件会自动热重载，不用重启 MaiBot。

### 第 3 步：确认模型

打开 `config/model_config.toml`，确认 `replyer` 和 `planner` 里至少有一个配了模型：

```toml
[model_task_config.replyer]
model_list = ["你的模型名"]
```

### 第 4 步：测试

在 QQ 里，用白名单里的号发：

```
/人格帮助
```

收到指令说明就说明插件跑通了。

### 以后怎么升级

- **git 安装的**：进 `plugins/qq-persona-manager/` 执行 `git pull`，然后在 WebUI 插件页点重载。
- **手动复制安装的**：重新下载新版，用新的 `plugin.py` 和 `_manifest.json` 覆盖旧的即可。
  **别删 `config.toml`**（里面是你的白名单和配置）。
- 升级后若插件页报配置缺少 `[plugin]` 段，按「六、出问题了？」里第一条处理。

## 三、使用

### 查询人格

```
/人格查询
```

> ⚠️ **默认只在私聊生效。** 群聊里用需要先打开"群聊执行开关"，见下一节。

你会收到一张合并转发卡片，里面三段：

- `#人设`：她是什么样的人
- `#行为风格`：什么时候说话、什么时候不说话
- `#表达风格`：怎么说话、用什么语气

> **标签会顶在每段正文最前面**（如 `#人设` 独占一行，下一行才是内容）。
> 因为合并转发的节点「发送者名字」在多数适配器上会被换成账号昵称，标签写在名字上
> 你根本看不到 —— 所以默认直接写进正文，一眼就能分清哪段是哪类。
> 如果你的适配器能正确显示节点昵称、不想要正文里的标签，把
> `[message] label_in_content` 关掉即可。

> **只读这三段。** 备用的人格会被完整忽略 —— 也就是 `[personality]` 段里的
> `multiple_reply_style`（备用表达风格）和 `multiple_probability`（随机启用备用风格的概率），
> 查询不显示、修改也不会碰，全程逐字节保持原样。

### 群聊执行开关（针对 /人格查询 与 /人格优化）

`/人格查询` 会把人格内容发出去，人多的地方容易刷屏；`/人格优化` 会消耗一次模型调用并改写人格。
所以这两条**默认都只在私聊生效**。

**打开方式**：WebUI →「插件」→「QQ 人格管理」→ **限用范围** 卡片 → 打开
**`query_allow_group`**（给 `/人格查询`）或 **`optimize_allow_group`**（给 `/人格优化`）→ 保存。

也可以直接改 `plugins/qq-persona-manager/config.toml`：

```toml
[scope]
query_allow_group = true       # false（默认）= 只有私聊能查；true = 群聊也能查
optimize_allow_group = false   # false（默认）= 只有私聊能优化；true = 群聊也能优化
```

两个开关**互相独立** —— 可以只开查询、不开优化，反之亦然。

**开关没打开时**，白名单用户在群聊里发指令，收到的是同一句提示：

> 暂不支持群聊使用此功能，请到插件页开启此功能群聊执行开关

**判定顺序**是：① 白名单 → ② 群聊开关。所以非白名单用户在群里发指令，收到的是"您无权进行此类操作"，不会泄露这个开关的存在。

> 这两个开关**只管 `/人格查询` 和 `/人格优化`**。`/人格修改` 和 `/人格帮助` 不受影响，群聊私聊都能用。
>
> 两条指令共用同一句群聊禁用文案（`query_group_disabled_message`），想改说法改这一个字段就行。

### 修改人格

```
/人格修改 说话加上喵~
```

或者同时提多个要求：

```
/人格修改 说话加上喵~，另外晚上11点以后就别发言了
```

会发生什么：

1. 插件的**模型**先判断需求属于哪一类（或哪几类）
   - **人设** = 她是什么样的人
   - **行为风格** = 什么时候说话、什么时候不说话
   - **表达风格** = 怎么说话、说什么话
2. 把需求**和对应分类的原文融合**，生成完整的新文本（不会丢掉你原来写的内容）
3. 写回 `config/bot_config.toml`，MaiBot 检测到文件变化后自动热重载
4. 在聊天流里回复：**人格已热更新成功**

如果需求跟这三类都不沾边（比如让它去执行一个外部任务、发乱码），会回复：

> 人格热更新失败，当前需求不匹配

**只发 `/人格修改` 不带需求**时，会回复：

> 请在指令后面带上修改需求

并且什么都不改。

> 人设改完只影响**新生成的回复**，已经发出去的消息不会变。想确认效果，连续聊几轮看风格。

### 优化人格

```
/人格优化
```

人格写长了以后，每次请求都要把这些字连同上下文一起发给模型 —— 字数越多，token 花得越多，
还容易让模型抓不住重点。`/人格优化` 就是干这个的：

1. **重新分类**：让模型按「她是谁 / 什么时候说话 / 怎么说话」把内容重新摆放一遍。
   这是为了解决模型自由发挥时**有概率分类错误**的问题（比如把"句尾加喵"这种说话规则写进了人设段）。
2. **压缩精简**：在**保持语义不变**的前提下，把重复、铺垫、举例之类的冗余删掉，
   保留全部设定与风格约束。
3. 写回 `config/bot_config.toml`，自动热重载。

结果只有两种：

- 优化成功 → 回复 **人格优化成功**，紧接着**再发一张和 `/人格查询` 一样的人格卡片**，
  直接看到优化后长什么样
- 优化失败 → 回复 **人格优化失败**（具体原因记在插件日志里）

> 那张回显卡片和 `/人格查询` 用的是**同一套渲染**（标签位置、`label_in_content` 开关、
> 超长截断、合并转发降级全都一致）。不想要这张卡片的话，把
> `[message] optimize_send_card` 关掉即可，优化照常生效。
> 卡片万一发不出去（比如适配器不支持合并转发又发不出文本），**不影响已经完成的优化**。

> ⚠️ **默认只在私聊生效。** 群聊里用需要先打开「`optimize_allow_group`」开关，
> 它和 `/人格查询` 的开关是**两个独立开关**。

**写入前的三道保险**（任一不过就判定为失败，**绝不动你的配置**）：

| 保险 | 拦住什么 |
|---|---|
| 三段不能全空 | 模型把人格清空 |
| 优化后总字数必须变短 | 模型没在压缩，甚至越改越长 |
| 优化后不能只剩原文两成以下 | 模型大段删内容、疑似丢失信息 |

另外，如果模型认为**没什么可优化的**（结果和原文一模一样），会回复
「人格已足够精简，无需优化」，不会白写一次文件 —— 这不算失败。

> 每次优化前都会自动备份（和 `/人格修改` 共用同一套备份），想回滚随时可以从
> `data/plugins/zhengyz233.qq-persona-manager/backups/` 里挑一个恢复。
>
> `[behavior] dry_run` 演练模式对它同样有效：只把结果发出来给你看，不写配置。

## 四、插件配置项说明

WebUI 里能改，也可以直接编辑 `plugins/qq-persona-manager/config.toml`。
完整默认内容见仓库里的 [`config.toml.example`](./config.toml.example)。

### `[plugin]` 插件信息

| 字段 | 默认 | 说明 |
|---|---|---|
| `config_version` | `"1.0.0"` | **配置结构版本号**，MaiBot 用它判断配置是否需要迁移。**必须存在且不能为空**，否则插件加载失败。由插件维护，平时不用改 |

> 这个版本号跟插件版本（`_manifest.json` 里的 `version`）是两回事，不用跟着插件升级而改。

### `[access]` 白名单与权限

| 字段 | 默认 | 说明 |
|---|---|---|
| `whitelist` | `[]` | 允许用指令的 QQ 号列表 |
| `deny_message` | `您无权进行此类操作` | 无权限用户收到的提示 |
| `notify_on_deny` | `true` | 关掉后无权限用户的指令会被静默忽略（不回复） |

### `[scope]` 限用范围

| 字段 | 默认 | 说明 |
|---|---|---|
| `query_allow_group` | `false` | **`/人格查询` 的群聊执行开关**。`false` = 只在私聊生效；`true` = 群聊也能用 |
| `optimize_allow_group` | `false` | **`/人格优化` 的群聊执行开关**。`false` = 只在私聊生效；`true` = 群聊也能用。与上一个开关互相独立 |
| `query_group_disabled_message` | `暂不支持群聊使用此功能，请到插件页开启此功能群聊执行开关` | 上面任一开关关闭时，白名单用户在群聊发对应指令收到的提示（两条指令共用） |
| `treat_unknown_scope_as_group` | `false` | 万一判断不出消息来自群聊还是私聊，按哪类处理。默认按私聊（不影响正常使用）；若你的适配器上报信息不全、群聊被误放行，改成 `true` |

### `[model]` 模型

| 字段 | 默认 | 说明 |
|---|---|---|
| `task_priority` | `["replyer", "planner"]` | 按顺序尝试的模型任务名。默认先用 replyer，不行自动换 planner |
| `temperature` | `0.2` | 分类温度，建议 0.1~0.3 |
| `max_tokens` | `4096` | 单次生成长度上限 |
| `timeout_seconds` | `120` | 等模型的最长秒数，超时换下一个任务名 |

### `[message]` 对外文案

| 字段 | 默认 | 说明 |
|---|---|---|
| `cat_personality` | `#人设` | 人设段的标题，同时作为该段正文最前面的标签 |
| `cat_behavior_style` | `#行为风格` | 行为风格段的标题，同时作为该段正文最前面的标签 |
| `cat_reply_style` | `#表达风格` | 表达风格段的标题，同时作为该段正文最前面的标签 |
| `label_in_content` | `true` | **把分类标签写进每段正文最前面**（标签独占一行，下面接内容）。合并转发的节点发送者名字常被适配器换成账号昵称，标签只写在名字上往往看不到，所以默认开启。关掉后只在合并转发的发送者名字上显示标签 |
| `need_requirement_message` | `请在指令后面带上修改需求` | 只发 `/人格修改` 没带需求时的提示 |
| `success_message` | `人格已热更新成功` | 修改成功后的提示 |
| `mismatch_message` | `人格热更新失败，当前需求不匹配` | 需求不属于任何一类时的提示 |
| `error_prefix` | `人格热更新失败` | 出现技术性错误时的提示前缀 |
| `optimize_success_message` | `人格优化成功` | `/人格优化` 成功的提示 |
| `optimize_failure_message` | `人格优化失败` | `/人格优化` 失败的提示（原因记在日志） |
| `optimize_nochange_message` | `人格已足够精简，无需优化` | 模型认为没啥可优化时的提示 |
| `optimize_send_card` | `true` | 优化成功后**额外发一张人格卡片**（和 `/人格查询` 一样），方便直接看优化后的效果。关掉后只回一句「人格优化成功」 |

### `[behavior]` 运行行为

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 插件总开关 |
| `dry_run` | `false` | **演练模式**：打开后只把判定结果发到聊天流，**不写入配置文件**。第一次用建议先开一次看看效果 |
| `ignore_quoted_commands` | `true` | **忽略「引用消息」里携带的指令**。开启后，别人引用你发过的 `/人格查询`、`/人格修改` 不会再次触发插件；本人正常发送不受影响。**建议保持开启** |
| `backup` | `true` | 写入前备份 `bot_config.toml`，**强烈建议保持开启** |
| `backup_keep` | `20` | 最多保留多少个备份 |
| `config_path` | `""` | `bot_config.toml` 的绝对路径。留空自动定位，一般不用填 |
| `max_requirement_length` | `500` | 单次需求最大字数 |

## 五、工作原理（想了解再看）

- 插件跑在 MaiBot 的独立 Runner 子进程里，只能使用 `maibot_sdk` 和 Python 标准库，**不 import 主程序**。
- 查人格时优先通过 `ctx.config.get("personality")` 读全局配置，读不到就直接解析 `config/bot_config.toml`。
- 改人格时用**文本级手术**：只替换 `[personality]` 段里 `personality` / `behavior_style` / `reply_style` 三个键的值，**其余内容、缩进、注释、别的段落一字不动**。
- `/人格查询` 与 `/人格优化` 的卡片回显**共用同一个渲染方法**，所以标签位置、`label_in_content` 开关、超长截断、合并转发降级行为天然一致，改一处两处都变。
- 写盘前会用 `tomllib` 做两道校验：① 整个文件语法能解析；② 目标字段确实变成了新值。**任何一道不过就中止，不会把配置写坏。**
- `/人格优化` 用的是另一套系统提示词：先按「谁 / 什么时候说话 / 怎么说话」重新归类，再在保留全部语义的前提下压缩。
  它对模型输出还有三道额外闸门（三段不能全空、总字数必须变短、不能只剩两成以下），**任一不过就不写盘**。
- 写盘前先把原文件备份到 `data/plugins/zhengyz233.qq-persona-manager/backups/`。
- **指令为什么要在入口做二次判定**：MaiBot 生成待匹配文本时会遍历所有消息组件，
  其中引用组件会把**被引用消息的正文原样拼到最前面**；而指令匹配除正则外还有一条
  `text.startswith(别名)` 的通路，没有结尾约束。所以「引用一条指令」会被当成本人发指令。
  插件因此改为**看消息段**：存在引用段时，要求指令必须出现在非引用的正文里才算数
  （对应配置 `ignore_quoted_commands`）。
- MaiBot 用 `watchfiles` 监听 `config/bot_config.toml`，检测到变化后热重载人格配置 —— 所以改完立即生效，不用重启。
- 判断消息来自群聊还是私聊时，先用消息对象里的 `message_info.group_info`（群聊才有）、`is_group_message` 等字段；万一这些都没有，就向宿主查聊天流列表，用 `stream_id` 反查 `chat_type`（结果缓存 5 分钟）。两层都拿不到才按 `treat_unknown_scope_as_group` 回退。

## 六、出问题了？

| 现象 | 原因 & 处理 |
|---|---|
| 插件页报「插件配置文件缺少 `[plugin]` 配置节，且必须提供 `plugin.config_version` 版本号」，提示"配置错误，业务暂停" | `config.toml` 缺少 `[plugin]` 段。**① 最简单**：把仓库里的 `config.toml.example` 复制过去、改名为 `config.toml` 覆盖；**② 手动**：在文件**最前面**补上这两行 `[plugin]` 和 `config_version = "1.0.0"`，保存。⚠️ 注意：只要文件里**有内容却缺这一段**，校验就会失败；文件整个为空反而会被自动补全。补好后插件会自动恢复运行 |
| 别人只是**引用了**我发过的指令，插件却被触发了 | v1.3.0 已修复。请确认插件版本 ≥ 1.3.0，并且 `[behavior] ignore_quoted_commands` 是 `true`（默认值就是）。原理：MaiBot 会把被引用消息的正文拼到待匹配文本最前面，插件只能在指令入口做二次判定把它拦掉 |
| 发指令完全没反应 | ① 白名单没填 → 所有人被拒（但这时应该会收到"您无权…"，如果连这个都没有就往下看）；② 插件没加载，去 WebUI 插件页看状态；③ 指令必须**以 `/` 开头**且单独成句 |

| 插件加载失败 | 看 MaiBot 日志。常见：`manifest_version` 不是 2、`maibot_sdk` 没装、MaiBot 版本低于 1.3.0 |

## 八、为什么插件要「直接写」配置文件？（设计说明）

这一节专门回答审核/使用者最常问的问题：**为什么本插件绕过宿主，用文件级写入改 `config/bot_config.toml`？**
—— 因为**当前 SDK 根本没有提供修改宿主全局配置的 API**，插件不是在"绕路"，而是"只有这一条路"。

### 8.1 SDK 只有只读接口，没有写入接口

插件运行在独立 Runner 子进程里，能碰到的配置能力全部是**只读**：

| 能力 | 作用 | 能否改宿主人格 |
|---|---|---|
| `config.get(section)` | 读宿主的某个配置段（如 `personality`） | ❌ 只读 |
| `config.get_plugin(...)` / `config.get_all()` | 读写**插件自己**的配置 | ❌ 只动插件自身，动不了宿主 |
| `component.update_plugin_config(...)` | 更新**本插件自己**的配置 | ❌ 同上 |
| `person.*` | 读取当前人格/人设 | ❌ 只读 |

也就是说：**没有任何一个接口能写宿主主配置**。要让"改人格"真正生效，只剩下"以文本方式改 `config/bot_config.toml`，
再让宿主的热重载（`watchfiles`）自己捡起来"这一种做法。

### 8.2 写入是怎么做的（尽量把影响面压到最小）

不是"整个文件重写"，而是**文本级手术**：

1. 先在内存里把 `config/bot_config.toml` 当**纯文本**读进来；
2. 只定位 `[personality]` 段，且只替换 `personality` / `behavior_style` / `reply_style` **三个键**的值；
3. **其余所有内容 —— 别的段落、注释、缩进、键序 —— 原样保留，一个字节都不动**；
4. 备用人格字段（`multiple_reply_style` / `multiple_probability`）**完全忽略**，任何针对它们的写入都会被闸门拒绝。

所以宿主里其他配置、其他插件写下的内容不会被动到，改动范围就是那三个键。

### 8.3 配置文件根目录是怎么找到的

写文件前得先知道 MaiBot 的根目录在哪。插件**优先用宿主通过 `ctx.paths` 提供的路径**
（`data_dir` / `runtime_dir`），取不到时才按 `cwd`、以及插件自身 `__file__` 的父目录逐级向上探测
`config/bot_config.toml`。探测按"从最可信到最兜底"的顺序，找到第一个存在的即用。

> 如果你的部署比较特殊（例如 `config/` 不在默认位置），把 MaiBot 日志里
> `定位 bot_config.toml` 那几行发出来，可以确认实际命中的路径。

### 8.4 已知限制与并发风险（诚实说明）

- **跨进程没有锁**：插件进程和宿主进程（含 WebUI 的配置编辑）是两个独立进程，写同一个文件时
  **没有跨进程文件锁**。理论上存在"宿主 WebUI 保存配置"与"插件写人格"同时发生的窗口，后写的会覆盖先写的。
  实践中这个窗口极窄（插件写盘在几十毫秒内完成），但**并非零风险**。
- **规避建议**：改人格时尽量不要同时在 WebUI 上手动编辑并保存同一份 `bot_config.toml`。
- 插件不会主动去写除了 `[personality]` 三个键以外的任何内容，因此即便发生覆盖，
  影响面也仅限于"这一次人格改动是否落地"，不会破坏文件其余部分。

### 8.5 已经内置的防护

即便只有"写文件"这一条路，也把安全做到位：

| 防护 | 说明 |
|---|---|
| 写前备份 | 改动前把原文件复制到 `backups/bot_config.<时间戳>.toml`，`backup` 默认开启 |
| `tomllib` 语法校验 | 写盘前先解析整份新内容，语法不通过就**中止、绝不写盘** |
| 目标字段确认 | 再校验目标键确实变成了新值，否则中止 |
| 字段白名单 | 只允许改那三个键，备用人格字段被硬拒 |
| `dry_run` 演练 | 打开后只把判定结果发到聊天流，**完全不写盘**，适合先观察 |

> 一句话总结：**SDK 无写入 API → 只能文本级写 `bot_config.toml` → 把改动面压到"三个键"、
> 并把备份/校验/白名单/演练四道闸门全部加上**，这就是本插件在现有 SDK 能力下能做到的最稳妥方案。
